# Firmware 3.5.0 board: smoke test on the real ESP32-S3 (2026-10-25)

**Question.** After the P0 fix (746756b), does the laptop actually read Wi-Fi CSI from
the ESP32-S3 on firmware 3.5.0, over USB and over the signed UDP link?

**Method.** New tool `aankhen/tools/smoke_board.py`. It lists serial ports without
opening an Arduino Uno, listens on each (it writes nothing) until a CRC-valid Aankhen
frame arrives, and counts for 20 s. For Wi-Fi it reads the key from
`data/app/esp32_link.json`, sends HELLO to UDP 47269, listens on 47270 and verifies each
datagram with HMAC-SHA256. It prints only the key's 8-character fingerprint and never
reads `secrets.h`. No relay command is sent.

## Findings (measured on the board on COM9, 303A:1001)

| Link | Result | Numbers |
|---|---|---|
| USB serial | **PASS** | aankhen-3.5.0, 6832 CSI frames in 20.0 s = **341 frames/s**, 64 subcarriers on every frame, 1 frame lost, 0 CRC errors; board STATUS: wifi connected, channel 9, csi_hz 350 |
| RSSI | weak | min -90, median -88, max -86 dBm |
| Wi-Fi UDP | **FAIL (network, not code)** | board STATUS net.key fingerprint = app key fingerprint (keys match); 3 HELLOs sent to the board's own reported IP, board counted 0 datagrams; `ping` from the laptop: "Destination host unreachable" (no ARP answer) |

- The P0 is fixed for USB: the board joins Wi-Fi now and streams CSI at ~340 Hz.
- The Wi-Fi link does not fail on HMAC. The laptop cannot reach the board at all on the
  LAN (layer 2). Probable causes, untested: the router isolates clients (often between
  its 5 GHz and 2.4 GHz bands, and the laptop is on the 5 GHz name), or the -88 dBm
  signal drops replies. The laptop's networks are also set to the Public profile, so
  the firewall rule (Private only) would not apply either. That is his setting to change;
  I did not touch it.
- -88 dBm is near the bottom of the usable range. Calibration done at this RSSI will be noisy.
