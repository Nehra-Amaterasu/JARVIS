# UI speed: bundle split and first paint (2026-10-25)

## Question
How big is the JARVIS desktop UI's production bundle, what loads before the first paint,
and does splitting the tabs into their own chunks (React.lazy) make the window paint sooner?

## Method
- `npm run build` in `app/ui` (Vite 8.3.4, rolldown, `target: es2022`), on f7682d0 before the
  change and after it. Sizes are the ones Vite prints (minified; gzip in brackets).
- What loads first comes from `dist/index.html`: the entry script plus its modulepreload links and CSS.
- What fills the entry chunk: a throwaway Vite config with a `generateBundle` hook that sums
  `renderedLength` per module (this is the size before minification, so read it as a ratio, not as bytes).
- First paint: headless Chrome 1440x900 driven over CDP by a scratch script. Cache off, CPU
  throttled 4x, 11 navigations per run, two runs per build taken in turn. Measures first-contentful-paint,
  plus the Performance-domain ScriptDuration and TaskDuration for the first 1.2 s.
  The page served by `vite preview` has no JARVIS server behind it (the shell plus "Server offline").

## Findings
1. Aankhen (three.js, 687 kB [180 kB]) and Mission (451 kB [137 kB]) were already lazy chunks.
   The galaxy view (MemoryGalaxy) is not in the bundle at all: only the dev demo page uses it.
2. Before the change the entry chunk was 383.5 kB [119.0 kB]. Most of it is react-dom, which
   cannot be split. After that, by unminified size: ConnectControls 26 kB, Core 22 kB, Yaadash 18 kB,
   FirmwareCard 18 kB, System 16 kB, Limbs 15 kB, PhoneCard 12 kB, RelayWiring 11 kB.
   Apart from Core, those are all tabs the window does not open on.
3. Core is the default tab (`sessionStorage 'jarvis.tab' || 'core'`), so it stays in the entry chunk.
   Every other tab moved to its own chunk (`src/pageLoaders.ts`).

| first load (index.html) | before | after (on f7682d0) | after rebase on 494b484 |
|---|---|---|---|
| JS | 403.9 kB [126.9 kB] | 305.9 kB [100.1 kB] | 306.4 kB [100.4 kB] |
| CSS | 125.5 kB [29.0 kB] | 110.2 kB [26.4 kB] | 110.2 kB [26.4 kB] |
| entry chunk | 383.5 kB [119.0 kB] | 280.3 kB [89.8 kB] | 280.5 kB [89.9 kB] |

New per-tab chunks: Yaadash 19.2 kB (with the new Learned and Reminders cards), Limbs 45.5 kB,
Connect 28.6 kB, System 8.6 kB. Total JS across all chunks is unchanged (1.60 MB): the code
moves, it does not shrink.

4. First paint did not change in any way I could measure. Median FCP across runs: before
   244-476 ms, after 244-772 ms. Median script time over the first 1.2 s: 60-91 ms before,
   71-73 ms after. Single runs ranged from 150 ms to 57 s, because the laptop was busy (see the
   10-15 laptop audit). The noise is larger than the effect. With the files coming from 127.0.0.1,
   about 100 kB less JS to parse is worth single-digit milliseconds at most.
5. Idle prefetch loads only the light tabs (Yaadash, Limbs, Connect, System), 2.5 s after start.
   Aankhen and Mission are never prefetched: evaluating three.js and the syllabus costs memory on a
   laptop already near its commit limit, and nothing is gained over the loopback network.

## What it changed
- `app/ui/src/pageLoaders.ts` holds the lazy loaders and the idle prefetch; `App.tsx` uses them (tested in `pageLoaders.test.ts`).
- I removed the Aankhen "Radar" layer chip, and the LD2450 wedge layer starts hidden (`twin/layers.ts`). The project is Wi-Fi only.
- Not done, and worth doing only if the window ever feels slow on Core: profile react-dom
  hydration of Core's cards, and the 110 kB global CSS (index.css). Neither can be fixed by splitting tabs.
